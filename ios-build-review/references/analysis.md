# Методика статического анализа

## Что действительно попадёт в приложение

В IPA исследуй все приложения в Payload. В XCArchive начни с Products/Applications. Сверь Info.plist архива с найденными продуктами. dSYMs можно применять для анализа после сопоставления UUID и архитектуры; xcarchive/dSYMs, SwiftSupport и метаданные архива сами по себе не являются лишними файлами внутри приложения. Подпись архива описывает состояние до экспорта, когда приложение ещё может быть переподписано. Формулируй выводы применительно к переданному артефакту.

В inventory.json пути продуктов заданы относительно product_base. resources содержит относительный путь и тип, определённый по сигнатуре, если он известен. Ищи дополнительные форматы по содержимому и привязывай их к ближайшему бандлу-владельцу. Ссылки из skipped_links не открывай. Ошибка чтения или неполная распаковка может объяснять последующий сбой проверки подписи. В таком случае предложи проверить оригинал или повторить экспорт.

## Бандлы, подпись и настройки

- Прочти бинарные и XML Info.plist, локализованные InfoPlist.strings, privacy manifests и фактически подписанные entitlements. Проверь типы значений, CFBundleExecutable и реальное наличие Mach-O нужной платформы. Проверь идентификаторы и версии встроенных расширений относительно приложения-хоста. Отличай исполняемый бандл от ресурсного.
- Для бандлов используй результат codesign --verify --strict. Отдельно проверь подпись автономных dylib и иных вложенных исполняемых файлов, например командой `codesign --verify --strict --verbose=2 "$image"`. Если различаются архитектуры, проверь подпись и entitlements по срезам. Различай нарушение целостности, неподходящий тип подписи, отсутствие цепочки доверия на машине и ошибку локального инструмента.
- Если есть embedded.mobileprovision, локально декодируй CMS через security cms -D или эквивалент. Сопоставь разрешённые идентификаторы, группы, team/application identifier, отладочные права и дату действия с подписанными entitlements и типом артефакта. Учитывай шаблоны профиля и исторические префиксы App ID. Отсутствующий профиль сам по себе не устанавливает дефект. Не публикуй идентификаторы устройств или содержимое сертификатов.

## Нативный разбор всех образов

Для каждого Mach-O изучи срезы и целевую платформу, LC_BUILD_VERSION или прежние version-min команды, зависимости, LC_RPATH, импортируемые и доступные определённые символы, секции и записи подписи/шифрования. Сборщик сохраняет otool -arch all -l и nm -arch all -m. При необходимости выдели срез во временный файл. Отфильтруй бинарные ресурсы, не являющиеся Mach-O, после проверки заголовка. Учитывай результаты по каждой архитектуре, в том числе различия между срезами.

Затем для каждого образа используй статический анализатор Mach-O или дизассемблер. Без REA на macOS можно начать с `otool -arch all -ov "$image"` для ObjC-метаданных и `otool -arch all -tvV "$image"` либо llvm-objdump для дизассемблирования. Сохраняй большие результаты локально и читай выборочно. Определи точки входа, регистрацию классов, плагинов и мостов, инициализаторы и обращения к системным сервисам. Проследи относящиеся к проверке обращения от функции или места регистрации до импорта, конфигурации или ресурса. Для статически включённого SDK укажи образ-владелец и свидетельство атрибуции, если оно есть. Отдельного файла у него может не быть. Если доступен только заголовок, защищённый участок или неподдерживаемый формат, укажи конкретный пробел. Для зашифрованного образа можно предложить соответствующий исходный XCArchive от разработчика.

Для подозрения на лишнюю библиотеку проверь входящие зависимости **всех** приложений, расширений и соседних библиотек. Разрешай @rpath, @loader_path и @executable_path в контексте загрузчика и хоста. Учитывай слабую линковку, re-export, транзитивные зависимости, автозагрузку плагинов и инициализаторы. LC_ID_DYLIB — собственное имя библиотеки. Проверь также dlopen, NSBundle, поиск классов по имени, реестры плагинов и ссылки из ресурсов или мостов. Рекомендация уместна, когда достаточно проверены потребители: «Для <путь к SDK> статических обращений не найдено. Проверьте динамическую загрузку и удалите SDK, если он не нужен». При существенных пробелах в этом поиске укажи пропущенную проверку.

## Прикладные слои и сочетания стеков

Активируй все подходящие проверки внутри каждого компонента. Для идентификации используй сочетание двоичного формата, ресурсов, зависимостей и точек регистрации. Имя файла или импорт WebKit — только подсказка.

| Стек | Что проверить в поставленном коде и ресурсах |
|---|---|
| Swift и Objective-C | Метаданные типов и протоколов, ObjC-классы и селекторы, Swift-символы и регистрации. Для релевантных вызовов свяжи импорт с местом обращения. Совпадение имени селектора само по себе не устанавливает использование непубличного API. |
| Flutter | Найди движок, Flutter assets, Dart AOT и точки регистрации нативных плагинов, включая add-to-app. Сопоставь method channels с обработчиками. Определи формат snapshot по артефакту; для кода AOT используй совместимый локальный статический декодер, если доступен. Если обработаны только нативные обёртки и assets, укажи, какая часть логики Dart осталась непроверенной. |
| React Native | Определи формат каждого JS-бандла по заголовку и содержимому. Текстовый Metro-бандл разбери статически, сопоставь модули, TurboModules или классический bridge с нативной регистрацией. Для Hermes установи версию байткода и используй совместимый дизассемблер Hermes в режиме чтения. Проследи обращения JS к модулям; не подавай бандл в JS-движок для исполнения. |
| Unity | Сопоставь UnityFramework или код хоста, данные игрока и нативные плагины. Для IL2CPP сопоставь global-metadata.dat с бинарником этой сборки и таблицами регистрации. Для Mono разбери упакованные managed assemblies локальным читателем IL. Учитывай загрузку плагинов и ресурсов из конфигурации Unity. |
| WebView | Найди инициализацию web view, фактическую загрузку страниц или файлов, bridge handlers и настройки навигации. Проверь локальные HTML, JS, конфигурацию и карты исходников, свяжи их с загрузчиком. Для удалённого контента опиши проверяемую локальную оболочку; при существенном пробеле укажи, какие ресурсы владелец может предоставить для статической проверки. Не открывай найденные URL. |

## От факта к рекомендации

- **Технические проблемы.** Дай путь и конкретное несоответствие. Различай ошибку конфигурации и ограничение наблюдения. Для технических требований Apple, например к форме privacy manifest, при необходимости проверь профильную документацию Apple.
- **Риски App Review.** Сопоставь вызовы чувствительных API с фактическими purpose strings и локализациями. Сопоставь privacy manifests приложения и SDK с обнаруженными обращениями. Для кандидата в непубличный API проверь наличие в публичном SDK и контекст обращения. Платёжная библиотека, разрешение или строка URL сами по себе не доказывают показ интерфейса, трекинг либо передачу данных. Включай условную рекомендацию, если конкретная находка и проверенный пункт правил дают разработчику предмет проверки.
- **Лишнее содержимое.** Ищи в поставляемых ресурсах и бинарниках тестовые данные, активные ссылки на staging, отладочные меню, исходные карты, упакованные профили разработки или возможные секреты. Проверь контекст: публичный клиентский идентификатор, демонстрационная строка в лицензии и рабочий приватный ключ имеют разный смысл. Укажи файл, ключ конфигурации или функцию, скрой само значение секрета; не проверяй его в сети.
